# Визуализатор графа зависимостей пакетов Alpine Linux

Практическая работа №2 по дисциплине «Конфигурационное управление», вариант 16.

## Общее описание

Консольный инструмент строит граф зависимостей пакета Alpine Linux (формат `apk`).
Зависимости читаются напрямую из индекса репозитория `APKINDEX.tar.gz`: менеджеры
пакетов и сторонние библиотеки для получения данных не используются, только стандартная
библиотека Python. Для тестов вместо реального репозитория можно указать текстовый файл
с описанием графа, где пакеты названы заглавными латинскими буквами.

Возможности:

- вывод прямых и транзитивных зависимостей (обход в ширину с рекурсией, ограничение глубины,
  корректная обработка циклов);
- вывод порядка установки зависимостей и сравнение его с `apk add --simulate`;
- описание графа на языке D2, изображение графа в SVG и сравнение графа с выводом `apk dot`.

## Требования

- Python 3.9 или новее.
- [D2](https://d2lang.com) для построения изображения (этап 5), проверка: `d2 version`.
- Docker или установленный `apk` для сравнения с настоящим менеджером пакетов
  (необязательно, нужно только для опции `--compare-apk`).

## Структура проекта

| Путь | Назначение |
|---|---|
| `src/main.py` | Командная строка, проверка параметров, вывод графа (этапы 1-3) |
| `src/alpine.py` | Скачивание и разбор `APKINDEX.tar.gz` |
| `src/graph.py` | Чтение тестового репозитория, рекурсивный BFS, вывод графа |
| `src/stage4.py` | Порядок установки, сравнение с `apk add --simulate` |
| `src/stage5.py` | Описание графа на D2, SVG-изображение |
| `src/apk_dot.py` | Сравнение графа с выводом `apk dot` |
| `tests/` | Модульные тесты и тестовые репозитории (`*-repository.txt`) |
| `scripts/demo_stage5.sh` | Визуализация трёх реальных пакетов с сравнением |
| `run.sh`, `run.bat`, `Makefile` | Запуск этапов 1-3 |
| `run_stage4.sh`, `run_stage5.sh` | Запуск этапов 4 и 5 |

## Параметры командной строки

Общие для всех этапов:

| Параметр | Описание |
|---|---|
| `--package NAME` | Имя анализируемого пакета (обязательный) |
| `--repository PATH_OR_URL` | URL репозитория Alpine или путь к тестовому файлу (обязательный) |
| `--test-mode` | Читать граф из локального тестового файла, а не из реального репозитория |
| `--max-depth N` | Максимальная глубина анализа, от 0 до 100 (по умолчанию 3) |

Этап 4 (`run_stage4.sh`):

| Параметр | Описание |
|---|---|
| `--install-order` | Вывести порядок установки (обязательный) |
| `--compare-apk` | Сравнить порядок с `apk add --simulate` (нужен реальный репозиторий) |
| `--apk-image IMAGE` | Docker-образ, если `apk` не установлен (по умолчанию `alpine:3.20`) |

Этап 5 (`run_stage5.sh`):

| Параметр | Описание |
|---|---|
| `--output FILE` | Путь к создаваемому SVG-файлу (по умолчанию временный файл) |
| `--no-open` | Не открывать изображение в программе просмотра |
| `--compare-apk` | Сравнить граф с выводом `apk dot` (нужен реальный репозиторий) |
| `--apk-image IMAGE` | Docker-образ, если `apk` не установлен (по умолчанию `alpine:3.20`) |

Ошибки в параметрах (неверное имя пакета, отсутствующий файл, неверный URL, глубина вне
диапазона, пакет не найден) выводятся в формате `Error: ...`, код возврата равен 2.

## Описание основных функций

- `alpine.parse_index` превращает текст индекса в словарь «пакет: зависимости». Версионные
  ограничения (`>=`, `=`, `~`) отбрасываются, оставляются имена.
- `alpine.read_apkindex` скачивает индекс и распаковывает его средствами стандартной
  библиотеки.
- `graph.read_test_repository` читает строки вида `A: B, C`.
- `graph.build_graph` строит граф рекурсивным обходом в ширину: каждый уровень обрабатывает
  отдельный вызов `_bfs_level`. Посещённые пакеты запоминаются, поэтому цикл не приводит
  к бесконечной рекурсии, а замыкающее ребро остаётся в графе.
- `stage4.build_install_order` упорядочивает пакеты алгоритмом Кана с очередью по алфавиту,
  результат детерминирован. При цикле выдаётся ошибка со списком пакетов цикла.
- `stage4.print_comparison` сравнивает порядок и состав пакетов с выводом APK.
- `stage5.build_d2` формирует описание графа на D2, корневой пакет выделяется цветом.
- `stage5.render_d2` вызывает `d2` и сохраняет SVG.
- `apk_dot.print_dot_comparison` сравнивает рёбра графа с рёбрами из вывода `apk dot`.

Зависимости вида `so:`, `cmd:` и `pc:` (библиотеки, команды, pkg-config) в граф не
включаются, учитываются только зависимости от пакетов по имени.

## Сборка и тесты

Сборка не требуется. Запуск тестов:

```bash
make test
```

или

```bash
python3 -m unittest discover -s tests -v
```

## Примеры использования

Этап 1-3, тестовый репозиторий с ромбом зависимостей:

```bash
./run.sh --package A --repository tests/diamond-repository.txt --test-mode --max-depth 10
```

```text
Dependencies of A (max depth 10):
A: B, C
B: D
C: D
D: (none)
```

Тестовый репозиторий с циклом:

```bash
./run.sh --package A --repository tests/cycle-repository.txt --test-mode --max-depth 10
```

```text
Dependencies of A (max depth 10):
A: B
B: C
C: A
```

Реальный пакет Alpine:

```bash
REPO=https://dl-cdn.alpinelinux.org/alpine/v3.20/main/x86_64/
./run.sh --package curl --repository "$REPO" --max-depth 2
```

Этап 4, порядок установки:

```bash
./run_stage4.sh --package A --repository tests/diamond-repository.txt \
    --test-mode --max-depth 10 --install-order
```

```text
Installation order for A:
1. D
2. B
3. C
4. A
```

Для цикла программа сообщает об ошибке, так как корректного порядка не существует:

```text
Error: Dependency cycle blocks installation order: A, B, C
```

Сравнение с настоящим менеджером пакетов:

```bash
./run_stage4.sh --package curl --repository "$REPO" --max-depth 100 \
    --install-order --compare-apk
```

Этап 5, описание на D2 и изображение:

```bash
./run_stage5.sh --package A --repository tests/diamond-repository.txt \
    --test-mode --max-depth 10 --output out/diamond.svg --no-open
```

Три реальных пакета с сравнением с `apk dot`:

```bash
./scripts/demo_stage5.sh
```

Скрипт строит графы пакетов `alpine-base`, `build-base` и `openssh`, сохраняет их в
`out/*.svg` и печатает сравнение. Репозиторий и глубину можно задать переменными
`REPOSITORY` и `DEPTH`.

## Сравнение с настоящим менеджером пакетов и возможные расхождения

Этап 4 сравнивается с `apk add --simulate`, этап 5 — с `apk dot`. Результаты могут
отличаться по следующим причинам:

- Анализатор не следует по зависимостям `so:`, `cmd:` и `pc:`. APK подтягивает по ним
  библиотеки и команды, поэтому в его выводе больше пакетов (например, `musl`).
- Часть пакетов уже установлена в образе Alpine, APK их не перечисляет.
- APK разрешает виртуальные пакеты (provides) и версионные ограничения, анализатор
  работает только с именами.
- Анализатор останавливается на глубине `--max-depth`, APK строит полный граф.
- Порядок пакетов с независимыми зависимостями у анализатора алфавитный, у APK
  определяется его решателем, поэтому допустимые порядки могут не совпадать.
- Анализатор при цикле порядок не строит, APK разрывает цикл сам.
